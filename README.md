# Vulnerability Tracker 

Тестовое задание для Kaspersky C# Developer. REST API на ASP.NET Core для управления уязвимостями и фоновыми задачами сканирования.

## Запуск

Команды выполняются из корня репозитория через `make`.
При запуске `make up-docker` или `make up-local` файл `.env` автоматически создаётся
из `.env.example`, если его ещё нет. Перед запуском можно создать `.env` самостоятельно
и указать свои значения настроек.

Для Docker требуется Docker Engine с Compose:

```bash
make up-docker
```

Остановка:

```bash
make down
```

Для локального запуска требуется .NET SDK 10:

```bash
make up-local
```

Локальный сервер работает в текущем терминале; для остановки нажмите `Ctrl+C`.
`make down` останавливает Docker Compose.

При настройках из примера API доступен по адресу `http://127.0.0.1:5147`.
Локальный профиль `http` включает Development: схема OpenAPI доступна по адресу
`http://127.0.0.1:5147/openapi/v1.json`. Compose запускает приложение в Production.

## Команды Makefile

| Команда | Назначение |

## Настройки .env

| Переменная | Пример | Назначение |
|---|---|---|
| `Api__Host` | `127.0.0.1` | IP-адрес привязки API на хосте |
| `Api__Port` | `5147` | Внешний порт, также порт локального запуска |
| `Api__InternalPort` | `8080` | Порт API внутри контейнера |
| `Scan__DelayMilliseconds` | `10000` | Длительность симуляции сканирования в миллисекундах |
| `Logging__Directory` | `./logs` | Папка с файлами логов на хосте |
| `Logging__ContainerDirectory` | `/app/logs` | Абсолютный путь к папке логов внутри контейнера |

Compose публикует `Api__Host:Api__Port` на `Api__InternalPort` контейнера. Адрес снаружи задаёт `Api__Host`.

## Эндпоинты

| Метод | Путь | Назначение | Тело запроса (JSON) | Успешный ответ |
|---|---|---|---|---|
| POST | `/api/vulnerabilities` | Создать уязвимость | `{"name":"SQL injection","level":9.5}` | `201 Created`, `{ "id": "..." }` |
| GET | `/api/vulnerabilities/{id}` | Получить уязвимость | Не требуется | `200 OK`, ID, название, критичность, дата создания |
| POST | `/api/scans` | Запустить фоновое сканирование | `{"repositoryUrl":"https://gitlab.example.com/team/project"}` | `202 Accepted`, `{ "id": "..." }` |
| GET | `/api/scans/{id}` | Получить статус сканирования | Не требуется | `200 OK`, ID, статус, время изменения, результат или ошибка |

Создание уязвимости:

```bash
curl -i http://localhost:5147/api/vulnerabilities \
  -H 'Content-Type: application/json' \
  -d '{"name":"SQL injection","level":9.5}'
```

Получение уязвимости - замените `<vulnerabilityId>` на `id` из ответа на создание:

```bash
curl -i "http://localhost:5147/api/vulnerabilities/<vulnerabilityId>" \
  -H 'Accept: application/json'
```

Запуск сканирования:

```bash
curl -i http://localhost:5147/api/scans \
  -H 'Content-Type: application/json' \
  -d '{"repositoryUrl":"https://gitlab.example.com/team/project"}'
```

Получение статуса и результата сканирования - замените `<scanJobId>` на `id` из ответа на запуск:

```bash
curl -i "http://localhost:5147/api/scans/<scanJobId>" \
  -H 'Accept: application/json'
```

Повторяйте запрос статуса, пока задача не перейдёт в `Completed` или `Failed`.

Оба POST-запроса возвращают `id` для последующего GET-запроса.
Поля `name` и `level` обязательны; `repositoryUrl` должен быть URL.
Статусы сканирования сериализуются строками: `Queued`, `Running`, `Completed`, `Failed`, `Cancelled`.
Даты возвращаются в UTC. `result` заполняется для `Completed`, `error` - для `Failed`.

Ошибки возвращаются в формате `{"message":<Описание ошибки>}`: `400` при ошибках входных данных,
`404` при отсутствии записи, `409` при конфликте, `500` при непредвиденной ошибке.
Ответ `500` не содержит внутренних деталей исключения. HTTP-метод, путь, код ответа
и длительность запроса выводятся в консоль и файлы; тела запросов не логируются.

## Логи

Логи записываются в `Logging__Directory` в файлы `api-YYYYMMDD.log` с ежедневной ротацией;
хранятся последние 14 файлов. Относительный путь при локальном запуске считается от папки
найденного `.env`, а при отсутствии файла - от content root приложения.
В Compose папка с хоста монтируется в `Logging__ContainerDirectory` (по умолчанию `/app/logs`), поэтому логи сохраняются после удаления
контейнера.

## Настройка фонового сканирования

Задержка задаётся в `.env`:

```dotenv
Scan__DelayMilliseconds=10000
```

Значение задаёт длительность имитации сканирования в миллисекундах и должно быть положительным.
Оно привязывается к `ScanSettings.DelayMilliseconds` через `IOptions<ScanSettings>`.
Если настройка не задана, используется 10000 мс. Недопустимое значение блокирует запуск хоста.

## Запуск задания

Из HTTP-обработчика вызовите зарегистрированный `IScanJobService`:

```csharp
var id = await scanJobService.StartScanJob(repositoryUrl, cancellationToken);
```

Метод сохраняет задачу со статусом `Queued`, помещает её ID в очередь и возвращает ID,
не ожидая завершения сканирования. Если постановка в очередь не удалась, задача получает
`Failed` или `Cancelled`, а исключение передаётся вызывающему коду.

`ScanJobWorker` последовательно читает очередь и создаёт отдельный DI scope на каждое задание.
Сервис выполнения меняет статус на `Running`, вызывает `SimulatedCodeScanner` с `Task.Delay`
из настроек, затем сохраняет `Completed` и текстовый результат. Репозиторий не скачивается
и фактический анализ кода не выполняется. Исключение сканера сохраняется в `Error` со статусом
`Failed`; следующие задания продолжают обрабатываться.

Статус, время его изменения и результат доступны через `GetScanJobStatusById(id)`.
Остановка хоста прерывает текущий `Delay` через `CancellationToken`, текущая задача получает
`Cancelled`. Отдельный эндпоинт отмены и настройка параллелизма пока не реализованы.

Репозитории и очередь находятся в памяти процесса и очищаются при перезапуске.
